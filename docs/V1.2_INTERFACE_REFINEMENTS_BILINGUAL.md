# v1.2 Interface Refinements / v1.2 接口细化说明

## 中文

v1.2 保持原有项目架构和成员分工不变。本轮实现加入了以下小范围接口细化：

- `run_agent()` 新增可信运行参数 `operator_approved: bool = False`；默认未批准。
- 调用 `issue_decision_letter` 时，loop 会覆盖模型提供的同名值，并注入真实
  `run_id`、运行配置中的 `autonomy` 和可信的 `operator_approved`。
- 模型 Action JSON 中的 `decision_record` 是普通字典；loop 会使用
  `FinalDecision.from_dict()` 验证并转换后再调用 write tool。
- `confirm` 模式采用 fail-closed：只有 `operator_approved=True` 才可能写入本地
  JSONL；未批准时返回 `CONFIRMATION_REQUIRED`。
- `suggest` 始终禁止写入；`act` 仍需通过既有事实检查和 guardrail；非法 autonomy
  返回 `INVALID_ARGUMENT`。
- 修正 `check_coverage` 对老师数据字段 `requires_preauth` 的读取。

### NOT_FOUND 错误代码说明

本轮不修改 Xiaohua 已实现的工具错误代码。当前工具使用更具体的代码：

```text
CLAIM_NOT_FOUND
MEMBER_NOT_FOUND
POLICY_NOT_FOUND
HOSPITAL_NOT_FOUND
NOT_FOUND
```

这是相对于最初统一 `NOT_FOUND` 方案的一项小型实现细化。下游 prompt、guardrail、
scripted backend、grader 和 evaluation 在当前开发基线中必须将上述五个代码都视为
“记录不存在”类别，不得只匹配字符串 `NOT_FOUND`。如果最终决定恢复为一个统一代码，
需先在全组确认并同步修改工具测试、descriptors 和 grader。

## English

v1.2 keeps the agreed architecture and ownership unchanged. This iteration adds
the following small interface refinements:

- `run_agent()` now accepts the trusted runtime setting
  `operator_approved: bool = False`; approval is denied by default.
- Before calling `issue_decision_letter`, the loop overrides any model-supplied
  values and injects the real `run_id`, configured `autonomy`, and trusted
  `operator_approved` value.
- The model supplies `decision_record` as a JSON object. The loop validates and
  converts it with `FinalDecision.from_dict()` before the write tool is called.
- `confirm` mode is fail-closed: a local JSONL write is possible only when
  `operator_approved=True`; otherwise the tool returns `CONFIRMATION_REQUIRED`.
- `suggest` never writes; `act` remains subject to fact checks and guardrails;
  an unknown autonomy value returns `INVALID_ARGUMENT`.
- `check_coverage` now reads the teacher dataset's correct `requires_preauth`
  field.

### NOT_FOUND error-code clarification

This iteration does not modify the tool error codes implemented by Xiaohua. The
current tools use the following specific codes:

```text
CLAIM_NOT_FOUND
MEMBER_NOT_FOUND
POLICY_NOT_FOUND
HOSPITAL_NOT_FOUND
NOT_FOUND
```

This is a small implementation refinement from the original single `NOT_FOUND`
proposal. Under the current working baseline, downstream prompts, guardrails,
scripted backends, graders, and evaluation code must treat all five values as the
same “record not found” category and must not match only the literal string
`NOT_FOUND`. If the team later decides to return to one generic code, that change
must first be agreed and then applied consistently to tool tests, descriptors,
and the grader.
